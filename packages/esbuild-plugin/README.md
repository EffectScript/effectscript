# effectscript-esbuild and effectscript-rollup — Build Tool Plugins Overview

## What They Are

`effectscript-esbuild` and `effectscript-rollup` are build tool plugins that extend
esbuild and Rollup respectively to treat `.efs` files as first-class module types. Like
the Vite plugin, each delegates compilation to the `CompilerHost` API and concerns itself
only with translating between the host build tool's plugin contract and the compiler's
transform interface.

These two plugins are documented together because they share a common origin story,
common architecture, and should share a common internal implementation via
`@effectscript/plugin-core`.

---

## Why Both Matter

### esbuild

esbuild is the fastest JavaScript bundler available and is used as the underlying
transform and bundling engine by several major tools — most notably Vite (in its dev
server transform pipeline), Remix, and many custom build pipelines. When a project uses
esbuild directly (rather than through Vite), `effectscript-esbuild` is the integration
point.

esbuild has a stable, minimal plugin API that is unlikely to change significantly. Its
plugin interface is intentionally simple: plugins intercept file load and transform
operations by namespace and filter. This simplicity makes the esbuild plugin the
lowest-complexity build integration to implement.

Library authors in particular frequently use esbuild directly for bundling their packages
before publishing to npm. Since EffectScript's library publishing story depends on smooth
toolchain integration, `effectscript-esbuild` is important for the library-author
workflow even if it's less visible than the Vite plugin.

### Rollup

Rollup is the canonical bundler for JavaScript library authors. It produces clean,
tree-shakeable ESM output that is preferred for npm packages. Many library tooling setups
— including those generated by `tsdx`, `tsup`, and `unbuild` — use Rollup under the
hood.

The Rollup plugin ecosystem is also the basis for Vite's plugin API (Vite extends
Rollup's plugin interface), which means a Rollup plugin written correctly will work in
Vite's build mode with minimal or no modification. This relationship makes the Rollup
plugin a high-leverage investment relative to its implementation cost.

## Shared Architecture: @effectscript/plugin-core

The core compilation logic is identical across all three build plugins:

1. Receive a file path and source content
2. Invoke the `CompilerHost` single-file transform API
3. Return emitted JavaScript and source map
4. Translate compiler diagnostics into the host tool's error/warning format

This logic lives in `@effectscript/plugin-core`, an internal package not published to
npm. Both `effectscript-esbuild` and `effectscript-rollup` (and `effectscript-vite`)
depend on it. Bugs fixed in `plugin-core` are fixed everywhere simultaneously.

`plugin-core` owns:
- `CompilerHost` lifecycle management (initialization, caching, teardown)
- Source map normalization to a common internal format
- Diagnostic severity mapping (error vs. warning vs. info)
- Diagnostic message formatting for terminal output
- Cache key computation (source content hash + compiler version)

Each individual plugin package is then a thin adapter of roughly 100–200 lines that
translates `plugin-core`'s interface into the host tool's plugin contract.

## esbuild Plugin

### How esbuild Plugins Work

An esbuild plugin is an object with a `name` string and a `setup` function. The `setup`
function receives a `PluginBuild` object and uses it to register callbacks:

- **`onResolve`** — intercept module resolution for paths matching a filter (e.g., all
  paths ending in `.efs`)
- **`onLoad`** — intercept file loading for resolved modules; return transformed content
  and a loader type

esbuild's model is simpler than Vite's: there is no separate dev/build mode, no HMR, and
no error overlay. An esbuild plugin either works or it returns an error object, which
esbuild surfaces in its terminal output.

### esbuild Plugin Responsibilities

**Module resolution (`onResolve`):** Register a resolver for the `.efs` filter that
resolves file paths to their absolute location on disk. This handles both explicit
`.efs` imports and extensionless imports where the `.efs` file should take precedence.
Must respect esbuild's `resolveDir` to correctly handle relative imports.

**File transform (`onLoad`):** Read the `.efs` file, invoke `plugin-core`'s transform
function, and return an `{ contents, loader, resolveDir, sourcefile }` object. The
`loader` should be `'js'` — esbuild then handles the resulting JavaScript natively.
Source maps should be inlined into the `contents` string using the `//# sourceMappingURL`
data URI convention, since esbuild's `onLoad` hook doesn't have a separate source map
return field.

**Error translation:** esbuild errors are objects with `{ text, location }` where
`location` includes `{ file, line, column, lineText }`. Compiler diagnostics must be
translated to this format precisely — esbuild uses the `lineText` field to render source
context in its terminal output.

**Declaration emit:** Unlike Vite, esbuild has no built-in concept of side-output files.
`.d.ts` declaration files should be written to disk as a side effect of the `onLoad`
hook when the plugin is configured to emit declarations. This requires that the plugin
know the output directory configuration.

### esbuild Configuration Interface

```typescript
interface EffectScriptEsbuildOptions {
  configPath?: string        // path to esc.json, defaults to cwd
  emitDeclarations?: boolean // write .d.ts files alongside JS output
  tsconfig?: string          // path to tsconfig.json for interop resolution
  logLevel?: 'silent' | 'errors' | 'warnings' | 'info'
}
```

### esbuild Constraints

esbuild is synchronous in its plugin execution model — `onLoad` and `onResolve` callbacks
can be async, but esbuild runs them with a timeout and expects fast resolution. The
`CompilerHost` single-file transform must complete in milliseconds for typical files. If
the transform is slow, esbuild's parallel build pipeline will stall waiting for the
plugin.

esbuild also does not support source map chaining the way Vite does — it merges source
maps from `onLoad` output into its own final source map. Testing this pipeline carefully
is important to ensure that debugging experience (original `.efs` line numbers in stack
traces) works end-to-end.

## Rollup Plugin

### How Rollup Plugins Work

Rollup plugins are objects with named hook functions. The lifecycle is more elaborate than
esbuild's, with separate hooks for different phases of the build. The relevant hooks for
EffectScript:

- **`resolveId`** — module resolution; same semantics as esbuild's `onResolve`
- **`load`** — file loading; return source content as a string
- **`transform`** — transform source content; return `{ code, map }` where `map` is a
  source map object
- **`buildStart`** — called once at build start; useful for initializing the
  `CompilerHost` instance
- **`buildEnd`** — called once at build end; useful for cleanup and declaration emit

Rollup's source map support is first-class: the `transform` hook returns a `map` object
separately from the code, and Rollup chains source maps from all transform plugins
together automatically. This is cleaner than esbuild's inline source map approach.

### Rollup Plugin Responsibilities

**Initialization (`buildStart`):** Instantiate a `CompilerHost` with the project
configuration. Holding a single `CompilerHost` instance for the duration of the build
allows for file-level caching across the module graph — if two entry points share a
common `.efs` dependency, it should only be transformed once.

**Resolution (`resolveId`):** Resolve `.efs` imports, handling both explicit extension
and extensionless import paths. Return `null` for non-`.efs` imports to let Rollup's
default resolver handle them.

**Transform (`transform`):** Invoke `plugin-core`'s transform function, return `{ code,
map }`. The source map must be a Rollup-compatible `SourceMap` object (not a string or
base64 data URI). `plugin-core` should normalize to this format.

**Declaration emit (`buildEnd` or `generateBundle`):** Write `.d.ts` files at the end of
the build, using Rollup's `this.emitFile` API so that declarations appear in the output
alongside the bundled JS. Using `emitFile` rather than direct filesystem writes allows
Rollup-based tools (like `vite build`) to include the declarations in their output
manifest.

**Watch mode:** Rollup's watch mode calls `buildStart` before each rebuild. The plugin
must reinitialize or reset the `CompilerHost` cache appropriately so that changed `.efs`
files are retransformed.

### Rollup Configuration Interface

```typescript
interface EffectScriptRollupOptions {
  configPath?: string
  emitDeclarations?: boolean
  tsconfig?: string
  include?: string | string[]  // micromatch patterns; defaults to ['**/*.efs']
  exclude?: string | string[]  // patterns to exclude
}
```

The `include`/`exclude` pattern follows the convention established by
`@rollup/plugin-typescript` and similar plugins, making the configuration familiar to
Rollup users.

### Rollup and Vite Build Mode

Since Vite's build mode uses Rollup under the hood, a correctly implemented Rollup plugin
will work in Vite build mode. This means `effectscript-rollup` effectively covers two
use cases: standalone Rollup builds and Vite production builds.

However, Vite adds its own plugin hooks on top of Rollup's API. A plugin written
exclusively against Rollup's API may not integrate correctly with Vite-specific behaviors
like the Vite module preload injection or the CSS code splitting. For this reason,
`effectscript-vite` remains the recommended plugin for Vite projects — it is Rollup-
compatible but also handles Vite-specific concerns. `effectscript-rollup` is for projects
that use Rollup directly.

## Shared Non-Goals

- **Implementing a bundler** — these plugins extend existing bundlers; they don't
  reimplement bundling logic.
- **Type checking during the build** — plugins surface transform errors (which prevent
  the build from completing) but are not substitutes for `esc check`. The distinction is
  important: `esc check` runs the full type checker; the plugin runs only enough to
  produce valid JS output.
- **HMR** — esbuild and Rollup do not have HMR systems; this is Vite-specific.
- **Supporting pre-v4 Vite or pre-v3 Rollup** — minimum version requirements should be
  set conservatively but not retroactively.

## Development and Release Sequencing

1. Build `effectscript-vite` first (highest impact, richest plugin API to learn from)
2. Extract `@effectscript/plugin-core` from the working Vite plugin
3. Build `effectscript-esbuild` against `plugin-core` (simplest plugin API, good validation)
4. Build `effectscript-rollup` against `plugin-core` (most featureful, but foundation is
   now shared)

This sequencing ensures the shared core is extracted from a working implementation rather
than designed speculatively, which reduces the risk of the abstraction being wrong for
one of the plugin APIs.
